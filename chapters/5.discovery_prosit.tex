This chapter describes the simulation model: how it is built from the event log,
what it has learned, and how it produces one simulated truck visit. The
experiments that selected and tested its parts are described in
Chapter~\ref{chp:experiments}; their results are in Chapter~\ref{chp:results}.
The model described here is the final configuration of E4
(Section~\ref{sec:exp_e4_runs}).

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{From Event Log to Executable Model}
\label{sec:sim_overview}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The model has two parts. The \emph{control flow} says which sequences of stops
a truck may perform. It is a Petri net discovered from the training log and
repaired with domain rules (E1, E2). The \emph{simulation parameters} say how
often each path is taken, which block a stop goes to, and how long trucks wait
and are served. ProSiT learns them from the same training log
\cite{Vinci2026prosit}. A small number of changes adapt the simulation loop to
the physical limits of the terminal (Section~\ref{sec:sim_adaptations}).

Figure~\ref{fig:sim_architecture} shows how these parts produce one simulated
visit. A truck arrives and receives its manifest. It then moves through the
control flow one step at a time. At each step, the learned routing gives every
possible next step a probability, the stop guard removes the steps that would
break the planned number of stops, and one step is drawn. For a yard stop, the
block, the waiting time and the execution time follow. The visit ends with Gate
Out.

\section{Control Flow}
\label{sec:sim_controlflow}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The control flow is a workflow net: a Petri net with one start and one end
place, in which every truck visit is one token that moves from Gate In to Gate
Out (Section~\ref{sec:bg_petri}). ProSiT executes the net, so it must be sound:
from every reachable state the visit can still end, and no token is left behind.

The net used in the simulation is the unfiltered Inductive Miner net IM 0.0,
restricted exactly to two domain rules and written as a state machine
(Figure~\ref{fig:sim_controlflow}). Its selection is described in E1 and E2
(Sections~\ref{sec:exp_discovery} and \ref{sec:exp_rules}). It accepts all 82
sequences of the training log and has ten places and 54 visible transitions.
Every place is a state of the visit, and every transition one possible next
step. A state machine is a Petri net in which every transition has exactly one
input and one output place \cite{Murata1989}. Several transitions can carry the
same activity label, which the labelled nets of ProSiT allow.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{figures/simulation_model/sim_control_flow_guard.png}
\caption{Control flow of the simulation model: IM 0.0 restricted to rules 3 and
5 as a state machine (10 places, 54 transitions, no silent transitions). The
labels show the stop guard of the simulator: $n$ is the number of planned stops
from the manifest and $c$ the number of stops done; a yard transition may fire
only if $c < n$, Gate Out only if $c = n$.}
\label{fig:sim_controlflow}
\end{figure}

Two properties of this form matter for the simulation. First, a truck holds one
token, so two of its stops can never be scheduled at the same time (rule 4).
Second, every decision is one choice among the visible next steps at one place.
ProSiT gives every transition a weight that depends on the case attributes and
on the activities done so far, but not on the marking of the net
\cite{Vinci2023Inf.Activ.Prob,Vinci2026prosit}. In a state machine, each
transition has one input place, so its weight automatically refers to one state
of the visit. In the original Inductive Miner net, the free order of the stops is
expressed by parallel branches that can be skipped by silent transitions, and
the skip decisions are then taken independently of each other. Decision points
are places with several outgoing arcs, and silent transitions are a known
difficulty for learning them \cite{PMRozinat2009}. The consequences for the
simulated visits are analysed in E3 (Section~\ref{sec:res_rq1}).

The stop guard is the only data condition of the model. It is not part of the
net, because ProSiT has no guards; it is applied in the simulation loop before
every routing draw. Together with the state machine it forms a simple data
Petri net with the planned stops $n$ and a counter $c$. From every reachable
state, a visit can still end with exactly $n$ stops, for every $n$ from one to
four, so the net with the guard is sound in the data-aware sense
\cite{FelliDeLeoniMontali2021}.

\section{Learned Components}
\label{sec:sim_components}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
% Draft notes by the author (kept):
% ProSiT is a probabilistic white box simulation model ... takes a petri net and an event log as its input and
% calculates several models accumulating to be one overall simulation model. It uses probabilistic decision trees,
% with distributions in its leaves, rather than static values ... the user can decide on the granularity of the
% learned trees (maximum tree depth, minimum amount of values per leaf). Multitasking: resources and their
% capacities from simultaneously executed activities. Workload features: queuing behaviour as features.

ProSiT learns every simulation parameter as a probabilistic decision tree
\cite{Vinci2026prosit}. The training log is first aligned with the net, so that
every event is assigned to a transition. For each component, a tree is then
trained on the features that are known at the moment the value is needed, for
example the manifest of the visit, the hour, or the number of trucks at a
resource. Each leaf holds a fitted distribution (exponential, normal, lognormal,
gamma, uniform or a constant) and the sample of training values it was fitted
on. In the simulation, the features of the current situation select one leaf,
and the value is drawn from its distribution, truncated to the range observed
in the leaf. ProSiT 1.0.4 chooses by cross-validation between a tree (depth one
to three, at least 50, 100 or 200 cases per leaf) and a single distribution,
using the continuous ranked probability score. Table~\ref{tab:sim_components}
lists the components; the settings are in Table~\ref{tab:sim_hyperparameters}.

\paragraph{Arrivals and manifests.} In generative runs, the time to the next
arrival is drawn from a tree on the weekday and hour of the last arrival
(Figure~\ref{fig:sim_tree_arrivals}). On weekdays between 5 and 21 hours, the
next truck follows after 0.5 minutes on average; at night and at weekends, the
mean gap is 2 to 35 minutes. The manifest of a generated visit is one training
manifest drawn as a whole, so that its attributes stay consistent. In the final
configuration, both are replayed from the period that is simulated: every
simulated truck arrives at the Gate-In time of one observed truck and carries
its manifest (Section~\ref{sec:exp_e4_design}).

\paragraph{Routing.} Every transition with alternatives has its own tree; it
predicts the probability that the transition fires when it is enabled. The
weights of the enabled transitions are then normalised. Of the 54 transitions,
38 have a tree and 16 a constant weight, mostly those without alternatives. The
trees split on the manifest. Figure~\ref{fig:sim_tree_routing} shows the tree
for an RMG receive as the first stop: for a receive visit with one planned stop
and mostly full containers, its probability is 0.88; for a delivery visit it is
practically zero. Figure~\ref{fig:sim_routing_first} compares the first stop that
the learned routing chooses with the training log, by flow type: the shares
agree within one percentage point.

\paragraph{Block choice.} ProSiT learns one tree per block for the probability
that a stop goes there, with the queue length and the workload of the block as
features. These trees learned that trucks prefer the block with the longer
queue, because the training data count a stop in the queue of its own block (E4,
Section~\ref{sec:res_mechanisms}). The final configuration therefore uses the
observed block of each stop; generative runs draw the block from the training
shares.

\paragraph{Waiting time.} One tree per resource predicts the time from the moment
a stop can start until it starts. In the final model, this time is measured from
the moment a lane of the block was free, not from the moment the whole block was
free (Section~\ref{sec:exp_e4_mechanisms}). The trees split mainly on the queue
length and the workload of the resource. At block T13
(Figure~\ref{fig:sim_tree_waiting}), the expected waiting time is 7 minutes with
at most one truck in the queue, 12 to 28 minutes with two to six, and more than
50 minutes with seven or more.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{figures/simulation_model/sim_tree_waiting_block.png}
\caption{Waiting-time tree of block T13 (final model): minutes from a free lane to
the start of the stop. All leaves on one scale.}
\label{fig:sim_tree_waiting}
\end{figure}

\paragraph{Execution time.} One tree per activity predicts the duration of a
stop. In the final model, it has one more feature: the number of other trucks at
the block when the stop starts (Section~\ref{sec:exp_e4_mechanisms}). For RMG
receives this feature makes the first two splits (Figure~\ref{fig:sim_tree_exec}).
Without reefer containers, a receive takes 7.5 minutes on average when the truck
is alone at the block, 11.7 minutes with one other truck, 16.0 with two and 20.8
with three; block T18 is slower. The tree for RMG deliveries has the same
structure.

\section{Execution of a Simulated Visit}
\label{sec:sim_execution}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The simulation processes the visits in the order of their arrival. For each
visit, the loop repeats four steps until Gate Out: determine the enabled
transitions of the current state; compute their routing weights and apply the
stop guard; draw one transition; for a yard stop, choose the block, determine
the start (waiting time, then the earliest time at which fewer than three trucks
are at the block during the whole stop) and draw the execution time. Every event
is written with its enabling, start and end time; times are floored to the
minute, as in the source systems.

\section{Adaptations to the Terminal}
\label{sec:sim_adaptations}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The simulation loop of ProSiT is not re-implemented. Its source is read at run
time, a few marked lines are changed by exact text replacement, and each change
can be switched off. With all changes switched off, the loop produces exactly the
same log as ProSiT. Table~\ref{tab:sim_adaptations} lists what each change does
and why it is needed; the evidence is in E3 and E4.

\section{Chapter Summary}
\label{sec:sim_summary}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The simulation model combines a repaired control flow, written as a state machine
with one data guard, and the probabilistic trees that ProSiT learns for routing,
arrivals, blocks, waiting and execution times. Its adaptations to the terminal
keep the physical limits: one stop of a truck at a time, as many stops as planned,
and at most three trucks at a block. How well the model reproduces the terminal is
reported in Section~\ref{sec:res_mechanisms}.
