\section{Goals of the Experiments}
\label{sec:experiment_goals}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The experiments assess whether a data-aware process simulation model can be
constructed from historical CTB truck-operation data and used as a credible
representation of the observed process. The aim is not to optimise the
terminal or to show that a more complex model is automatically better. The
aim is to test what the discovered model reproduces, where the discovery
workflow requires domain intervention, and what can be learned from its
responses to controlled operational changes.

The first goal is to construct an executable simulation model from the event
log while preserving the physical sequence of a truck visit. The expected
workflow starts with automatic process discovery. Its output is checked not
only through process-mining quality measures but also against the case
contract of one Gate In, sequential yard handling, and one final Gate Out. If
the discovered structure violates this contract, the experiment must make the
required correction explicit instead of treating a formally valid model as an
operationally valid simulation.

The second goal is to measure how well the resulting simulation reproduces an
unseen period of terminal operation. This includes the activity sequence,
service times, truck turnround times, and the arrival process. Four ProSiT
configurations form a factorial comparison of manually constructed workload
proxies and the simulator's native dynamic workload state. More context is
treated as a modelling choice, not as an expected improvement.

The third goal is to examine the model as a white-box tool for operational
what-if analysis. Historical fidelity and intervention validity are treated as
different requirements. A parsimonious model may reproduce a held-out log but
still omit the state through which an intervention should act. Candidate
models are therefore exposed to a resource-pool change at T22 and to a higher
truck-arrival rate. These interventions require different mechanisms: T22
tests resource-pool configurability, whereas increased demand tests whether
an endogenous workload state can transmit arrivals to delay. The experiments
test whether the specified input changes reach the simulation and whether the
resulting KPI changes are interpretable within the model boundaries. They do
not establish that the same effects would occur in the real terminal.

Across these goals, robustness is assessed through a temporal hold-out,
repeated simulation runs, model-quality diagnostics, and sensitivity checks.
Together, these experiments provide the evidence required to answer the
research questions introduced in Chapter~\ref{chp:introduction}.

\subsection{Layered Validity Audit}
\label{sec:layered_validity_audit}

The experimental design evaluates a sequence of distinct validity claims.
First, the event semantics must preserve the recorded order and case
boundaries. Second, the process model must replay held-out behaviour without
violating the sequential truck contract. Third, the stochastic model must
reproduce held-out routing, timing, arrivals, and case outcomes. Fourth,
observed change between the discovery and evaluation periods must be measured
before simulation error is interpreted. Fifth, resource and location labels
must be checked against their physical meaning. Only after these layers does
scenario response become evidence relevant to counterfactual decision support.

The layers are evaluated in this order because a strong result in one
perspective does not establish validity in another. Near-perfect replay fitness
can, for example, coexist with incorrect service times or physically
implausible resource behaviour. Simulation validation must therefore examine
control flow, time, resources, data and scenario response separately
\cite{Chapela2025SimQuality,Sargent2013Validation}.

The layers are complementary rather than alternative metrics. A failure at a
later layer does not invalidate every earlier result. It limits the conclusion
that can be drawn. For example, a net may be structurally sound and replay the
hold-out while its simulator still omits physical transition time. Likewise, a
parameter can be changed reproducibly without the model containing the
mechanism through which the real terminal would react. The results chapter
therefore reports both the successful layer and the first unsupported stronger
claim instead of assigning one global validity score.

\section{Solution Architecture}
\label{sec:solution_architecture}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The solution architecture is organised as a sequence of persistent processing
blocks. Each block produces an artefact that is used by the next block. This
makes the split, model discovery, simulation, and evaluation reproducible and
prevents information from the test period from entering model discovery.
Figure~\ref{fig:research_design} gives an overview of the complete pipeline.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth,trim=0 0 0 105,clip]{figures/schemas/experimental_pipeline_bw.png}
\caption{Solution architecture of the final experimental pipeline. Parameter
discovery uses the standardized $2\times2$ feature-source design in
Table~\ref{tab:prosit_hyperparams}. Every cell shares the temporal partitions,
Petri-net skeleton, runner and replication protocol.}
\label{fig:research_design}
\end{figure}

The input is the simulation-ready event log from
Chapter~\ref{chp:case_study_and_data}. It is divided chronologically into
discovery, validation, and test partitions. Only development-period data are
used to discover the control flow and the ProSiT simulation parameters. Within
each case, the physical stop sequence is stored as
\texttt{case:event:order}. The XES export and import preserve this sequence
instead of sorting tied or overlapping events by timestamp. An Inductive-Miner
model is then discovered from the ordered traces. A hard structural check
rejects any model containing a
parallel operator because terminal experts confirmed that the activities of
one truck must be sequential. The
accepted Petri net becomes the common control-flow skeleton for all simulation
configurations.

ProSiT first discovers arrival, timing, routing, and resource parameters from
the 64\,\% discovery partition. The four configurations differ only in whether
static workload proxies and native dynamic workload state are available to
their decision models. Each discovered parameter bundle is stored separately
and simulated over the same time window and case volume as the 16\,\%
validation partition. After the historical-fidelity comparison, the required
configurations are rediscovered on the complete 80\,\% development period.
Repeated runs with different seeds produce the simulation logs used for the
fidelity comparison and confidence intervals.

The evaluation block compares the simulated logs with the held-out event log
from several perspectives. It checks control-flow coverage, timing
distributions, point statistics, arrival behaviour, and resource assumptions.
The configuration selected for historical fidelity is used for RQ1. The later
demand audit then tests whether that selection has retained the endogenous
state required by the intended intervention. When it has not, the least complex
native-state configuration is used as an exploratory mechanism probe for RQ4.
This is not a second confirmatory selection of a validated forecasting model.
The scenario runner changes only the defined input parameters and compares each
intervention with a matched-seed baseline.
The transition-time scale check and the documented ProSiT
workarounds provide additional diagnostic evidence around the main pipeline.

\section{Temporal Train/Validation/Test Split}
\label{sec:train_test_split}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\paragraph{Why a Temporal Split Is Used}

A temporal split was chosen because the intended application learns a
simulation model from past operations and applies it to a later operating
period. A random split would mix earlier and later cases in both partitions and
could conceal changes in activity composition, workload or performance. The
last-block design follows the forecasting principle that evaluation data must
occur after the data available for model construction
\cite{BergmeirBenitez2012}. The final 20\,\% remain an untouched test period,
consistent with the outer temporal 80/20 convention used in the ProSiT
evaluation \cite{Vinci2026prosit}. The preceding 80\,\% are treated as the
development period and split once more in chronological 80/20 proportions.
This produces 64\,\% discovery data ($0.8\times0.8$) and 16\,\% validation data
($0.8\times0.2$) relative to the complete log. The exact percentages are a
pragmatic allocation, not a value prescribed by ProSiT or a universal
statistical optimum. They preserve the already defined final test period,
provide 57,254 cases for discovery, and leave 14,314 later cases for a
selection period comparable in duration to the final test window.

The validation partition is used only to select among the four candidate
configurations. After selection, the chosen configuration is
rediscovered on the combined 80\,\% development period and evaluated once on
the final 20\,\%. Each truck visit is assigned as a complete case so that no
part of a visit can enter two partitions. This design tests temporal transfer
under the observed case-study conditions. Separating model selection from the
final performance estimate avoids the selection bias that arises when the same
finite sample is used for both purposes
\cite{CawleyTalbot2010,ChapelaCampa2023Trust,Ozdemir2025UtilityBPS,vinci2025onlinediscoverysimulationmodels}.
Both cutoffs and all three case partitions are persisted and reused unchanged.

\paragraph{Status of the Evaluation Set}

The final 20\,\% are not inspected during feature-source selection. The
four-cell comparison is performed only on the 16\,\% validation period. The
test period is then used for the reported historical-fidelity estimate of the
selected historical-fidelity configuration. This is a genuinely untouched temporal test
within the case study, although it remains a retrospective evaluation of one
terminal and is not a prospective field validation of future interventions.
No scenario parameter is fitted to either validation or test outcomes.

\paragraph{Split Definition}
\label{sec:split_definition}

Let $\mathcal{L}=(c_1,c_2,\dots,c_N)$ be the set of $N=89{,}460$ cases
in the final event log. For each case $c_i$ let $\tau(c_i)$ denote its
earliest event timestamp:
\begin{equation}
    \tau(c_i)=\min\bigl\{
      \text{start}(e),\text{time}(e)
      \mid e\in c_i \bigr\}.
\end{equation}
Sort the cases by $\tau$ and a seeded deterministic tie break for equal
timestamps. The first 57,254 cases (175,902 events) form the 64\,\% discovery
partition. The next 14,314 cases (44,146 events) form the 16\,\% validation
partition, beginning at 2026-04-10 15:50. The final 17,892 cases (55,360
events) form the 20\,\% test partition, beginning at 2026-04-20 18:17. Their
union is the complete 89,460-case log and no events are dropped. A persisted
split manifest records the case counts, both temporal cutoffs and source-file
hashes. The simulation case count and start time are always read from the
manifest corresponding to the partition being evaluated.

\subsection{Temporal-Transfer Diagnostic}
\label{sec:temporal_transfer_method}

A temporal hold-out split was chosen for this study because the simulator is
intended to reproduce a later operating period rather than the observations
from which it was learned. A discrepancy against the later log can nevertheless
contain both simulation mismatch and a real change in terminal operations.
Treating the complete discrepancy as model error would confound model quality
with temporal process change \cite{Ozdemir2025UtilityBPS}. The observed
training and evaluation logs are therefore compared before the simulation
distances are interpreted. The audit covers case turnaround, per-activity
service distributions, activity and target-area composition, and the available
demand and utilisation attributes.

Wasserstein distance describes the magnitude of a distributional shift. For
the mean-turnaround difference, the two sets of truck visits are independent,
unequal in size and not assumed to have equal variance. A Welch interval is
therefore used \cite{Welch1947}. P90 is a sample quantile rather than a mean, so
its uncertainty is estimated by resampling complete cases within each period.
The percentile bootstrap uses 1,000 repetitions and reports the 2.5th and
97.5th percentiles of the resampled P90 differences
\cite{EfronTibshirani1993}. Resampling cases rather than events keeps the truck
visit as the statistical unit. Section~\ref{sec:stochastic_replication_ci}
distinguishes these sampling intervals from the Monte-Carlo intervals across
simulation seeds.

The audit is descriptive and does not refit or correct the model. For means,
the final difference between the observed evaluation period and the simulation
mean can be written exactly as
\begin{equation}
\bar{T}_{\mathrm{test}}-\bar{T}_{\mathrm{sim}}
=
(\bar{T}_{\mathrm{train}}-\bar{T}_{\mathrm{sim}})
+(\bar{T}_{\mathrm{test}}-\bar{T}_{\mathrm{train}}).
\label{eq:mean_transfer_decomposition}
\end{equation}
The first term compares the simulation mean with the observed training-period
mean. The second term is the observed change from the training period to the
evaluation period. Their sum equals the final mean deficit by algebra. This is
an accounting identity, not a causal attribution of individual cases or
mechanisms. It is not applied to Wasserstein distances because distributional
distances do not have the same additive decomposition.

The temporal-transfer audit loads the two frozen real partitions, constructs
one turnaround observation per case and computes the real-period distribution,
composition, Welch and bootstrap diagnostics. It neither loads simulated logs
nor repeats model discovery. The
simulation mean in Equation~\ref{eq:mean_transfer_decomposition} comes from the
standardized ten-seed evaluation reported in Chapter~\ref{chap:results}. The
equation combines these separately reported summaries.

\section{Process Discovery}
\label{sec:process_discovery_methodology}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\subsection{Discovery Input and Event-Order Semantics}

In a data-aware process-simulation workflow, control flow is discovered before
the timing, routing, arrival, and resource parameters are fitted. For ProSiT,
the resulting Petri net is not merely a diagram: it is the executable backbone
that determines which transition can fire next. The selected control-flow model therefore
has to balance fitness, precision, generalisation, and simplicity while also
respecting the physical meaning of a truck visit
\cite{Leemans2014InductiveMiner,PMvanDerAalst2016}.

The CTB domain restriction is deliberately narrow. Within one case,
\texttt{Gate In} must precede the yard work and \texttt{Gate Out} must follow
it. Two activities of the same truck may not execute in parallel. Different
trucks may still be processed concurrently through the simulator's resource
capacities. The order among yard activities is not constrained because it
depends on the handling requirements of the visit and repetitions are
operationally possible. The no-parallelism constraint was confirmed by
operational experts from the terminal and fixed before inspecting the
discovered model.

The resulting discovery problem differs from the long, largely acyclic chains
that are common in administrative business-process examples. A truck visit is
constructed from a small activity vocabulary and a fixed gate boundary. Its
internal behaviour consists mainly of different sequential combinations and
occasional repetitions of the same yard services. The dominant heterogeneity
is therefore not the number of activity labels, but the selected combination,
their order, the responsible terminal area, and the strongly varying service
and pre-service durations. This pattern is typical of logistics operations in
which a limited set of handling functions is repeated under changing demand,
utilisation, routing and resource conditions. A compact activity alphabet does
not make the process trivial to simulate. It shifts the relevant modelling
question from discovering a long nominal path to reproducing the frequencies,
timing, resource contention and context-dependent performance of many short
physical executions.

The domain input was collected as a project-level requirements and
plausibility review with CTB operational experts rather than as a formal
qualitative interview study. The experts confirmed that every relevant visit
starts with \texttt{Gate In}, ends with \texttt{Gate Out} and contains at least
one yard activity. Yard activities may occur in different orders and may be
repeated. Delivery commonly precedes receive, but no predecessor-successor
combination was identified as physically impossible. A visit containing only
\texttt{LL\_mixed} between the two gate events is valid, while a gate-only
visit is not. The experts also confirmed that one truck cannot execute two
activities in parallel and that three RMGs per block is a hard upper bound.
They regarded the retained two-month period as representative of the relevant
case types after overlong records attributed to system errors had been removed.
These judgments validate the stated case contract and capacity ceiling. They
do not validate fitted distributions, queue semantics, spatial
interchangeability or scenario effects. No interview transcript or inter-rater
score was produced, which limits this evidence to a domain requirements check.

The physical stop order in the source schedule is given by
\texttt{ANLAUFPUNKT\_SEQUENZNUMMER}. During event-log construction this order
is stored as the numeric attribute \texttt{case:event:order}, with
\texttt{Gate In} at the first and \texttt{Gate Out} at the last position. The
XES trace therefore has an explicit within-case order that is independent of
the event timestamps. Equal source sequence numbers are resolved by reported
ready time and then by stable source-row order. Chapter~\ref{chp:case_study_and_data}
describes this construction and its assumption that the operational schedule
sequence is the best available representation of the executed stop order.

An initial diagnostic conversion through a PM4Py DataFrame formatter sorted
events by timestamp. Because CTB timestamps have minute resolution and may
overlap, that conversion changed the stored trace order. The authoritative
pipeline instead preserves \texttt{case:event:order}, while the original timestamps
remain unchanged for the time and resource models. A direct audit shows that
completion-time sorting changes the sequence of 11 among 89,460 visits. This
input correction is necessary, but it does not by itself guarantee a
physically admissible discovered model. Even with the intended event order,
Inductive Miner may interpret frequently reversed directly-follows relations
as concurrency. In CTB these relations express alternative sequential routing,
not simultaneous service of one truck.

The frequency view confirms a stable outer process boundary: every training
case enters through \texttt{Gate In} and ends at \texttt{Gate Out}. Most visits
contain one yard activity. The prominent connection from
\texttt{LL\_delivery} to \texttt{RMG\_receive} shows the principal
multi-operation sequence.
\texttt{RMG\_receive}, \texttt{RMG\_delivery}, and \texttt{LL\_delivery}
dominate the handling volume. These directed connections describe succession,
not simultaneous execution: terminal experts confirmed that one truck does
not perform two activities in parallel. The DFG is therefore useful
descriptive evidence, but it is not used directly for simulation because it
has no marking or firing semantics and cannot itself distinguish choice from
concurrency.

The raw Inductive-Miner tree is retained as a discovery diagnostic. On the
64\,\% discovery partition it contains three parallel operators and an
optional complete yard section. The first property conflicts with the
expert-validated single-truck semantics, while the second permits the invalid
trace \texttt{Gate In} $\rightarrow$ \texttt{Gate Out}. The raw tree is
therefore not silently presented as an operationally valid source model.

Before ProSiT parameter discovery, a pre-specified source-model repair maps the
observed activity alphabet to the validated CTB case contract. The repaired
process tree has the form
\begin{equation}
\operatorname{sequence}\!\left(
\texttt{Gate In},
\operatorname{loop}\!\left(
\operatorname{xor}(a_1,\ldots,a_k),\tau
\right),
\texttt{Gate Out}
\right),
\label{eq:ctb_control_flow_contract}
\end{equation}
where $a_1,\ldots,a_k$ are the yard activities observed in the discovery
partition. The loop executes its visible choice at least once and may repeat
it. Consequently, the model permits arbitrary sequential yard orders and
repetitions, but neither within-truck parallelism nor a gate-only visit. This
repair does not prescribe which yard order is frequent. ProSiT still learns
routing weights, activity durations, waiting times and resource behaviour from
the event log.

This distinction is methodologically important. The raw tree is the outcome
of automatic process discovery. The executable Petri net is a transparent,
expert-supported repair of that outcome. Calling the latter an unchanged
Inductive-Miner model would overstate automation. Conversely, rejecting the
entire discovery approach because a concurrency cut is physically unsuitable
would discard the useful evidence that the process consists of a compact,
highly variable yard-activity language.

\includegraphics[width=\textwidth,height=0.48\textheight,keepaspectratio]{figures/discovery/petri_net_inductive.png}
\caption{Expert-constrained sequential Petri net used as the common ProSiT

The repair follows the general principle demonstrated in state-aware
stochastic simulation research that an automatically obtained source net may
require an explicit domain correction before it is used for experiments
\cite{Vinci2023Inf.Activ.Prob}. Simulation-guided control-flow repair further
shows why the discovered and repaired languages should be distinguished and
evaluated rather than conflated \cite{SimulationGuidedRepair2025}. The CTB
adaptation is fixed from the terminal case contract, not inferred from
validation performance. It is applied identically to all four ProSiT
configurations. The factorial comparison therefore cannot favour one feature
configuration through a different Petri net.

The repaired model deliberately generalises beyond exact observed variants.
It permits unseen sequential combinations because experts identified no
physically excluded predecessor-successor pair. This is a strong abstraction
and its routing-frequency fidelity must be tested empirically through activity
rates and NGD ($N=3$). The earlier prefix-trie fallback is not part of the final
methodology.

\subsection{Held-Out Conformance and Case-Contract Validation}

The executable net is evaluated on the discovery, validation and final test
partitions through
token-based replay fitness and precision, together with PM4Py's
\texttt{generalization\_tbr} and \texttt{simplicity\_petri\_net} measures.
Fitness tests whether observed traces can be replayed. Precision penalises
behaviour allowed by the model but not supported by the log. Generalisation
rewards an abstraction that is not tied to individual observations. Simplicity
describes structural economy. No single metric establishes model
suitability. Their joint interpretation is combined with the explicit
structural check that counts parallel operators and with simulation-output
contracts.

The generated logs are also checked against the sequential case contract. Each
case must contain one initial \texttt{Gate In} and one final \texttt{Gate Out}.
Activities inside one case may not overlap, \texttt{Gate Out} may not precede
yard work, and completion timestamps may not decrease. Gate-only paths and
within-case overlap are hard contract violations for the repaired model. This
separates replay coverage from physical sequence validity. The results are
reported in Section~\ref{sec:results_process_discovery}.

\section{Simulation Parameter Discovery Configurations}
\label{sec:simulation_discovery_methodology}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

ProSiT is used unchanged as the discovery and simulation engine
\cite{Vinci2026prosit}. All simulation parameters are learned by
\texttt{SimulatorParameters.discover\_from\_eventlog} from the training
partition only. The final comparison is a $2\times2$ feature-source design.
Visit, process, container and location attributes are available in every
cell. Factor $S$ controls the manually constructed static demand and
utilisation proxies attached to a visit. Factor $N$ controls ProSiT's native
dynamic \texttt{workload} and \texttt{queue\_length} state. Holding the Petri
net, split, discovery settings and simulation seeds fixed separates the two
information sources and tests whether their joint use changes the effect of
either source.

\subsection{Compared Configurations}
\paragraph{Common decision-tree specification}

All four configurations use \texttt{max\_depth\_tree}$=3$,
\texttt{min\_samples\_leaf\_cv}$=[50,100,200]$, and
\texttt{random\_state}$=42$. Timing, routing and resource-selection models can
therefore use decision trees whose leaves carry local distributions. For the
temporal models, the implementation selects among candidate leaf sizes using
Wasserstein-distance-based cross-validation. It does not use CRPS. A candidate
tree that provides no useful validation improvement remains pooled. This
internal safety measure and all other discovery logic are identical across cells.

Depth three follows the standard ProSiT specification used as the controlled
framework configuration in this study \cite{Vinci2026prosit}. It permits up to three successive
binary partitions and is sufficient to express interactions among visit,
location and workload state without producing very small terminal leaves.
Deeper trees were not screened because tree depth was not a research factor:
testing several depths on the same validation period would add another layer
of model selection and increase the risk of attributing sample-specific splits
to operational mechanisms. The minimum-leaf cross-validation already controls
local sample support within the fixed depth. The conclusion is therefore
conditional on the standard depth-three ProSiT configuration and the thesis does
not claim that depth three is globally optimal for CTB.

\paragraph{Configuration \textit{visit-only}}
\label{sec:cfg_rules}

The common state contains \texttt{process\_flow\_type}, stop, receive and
delivery counts, container descriptors, visit complexity,
\texttt{primary\_target\_area}, and \texttt{target\_area}. Static demand and
utilisation proxies and derived load bins or ranks are removed, and
\texttt{use\_workload\_features=False}. This cell is deliberately blind to
both workload sources. It is the parsimonious reference cell against
which their incremental value is assessed.

\paragraph{Configuration \textit{static-only}}

The manually prepared demand, utilisation, target-load, bin and rank
attributes are added to the common state, while ProSiT's native workload
features remain disabled. This cell tests whether workload information already
attached to the historical visit improves transfer to the later period.

\paragraph{Configuration \textit{native-only}}

The static proxies remain removed and
\texttt{use\_workload\_features=True}. ProSiT can then add current workload
(concurrent tasks) and queue length (enabled tasks not yet started) to the
waiting-time and resource-selection models. This cell isolates the simulator's
own dynamic state abstraction from the manually engineered proxies.

\paragraph{Configuration \textit{both}}
\label{sec:cfg_workload}

The full static attribute set and ProSiT's native dynamic state are available
together. This is the most context-rich cell, but it is not assumed to be the
best configuration for every purpose. Comparing it with \textit{static-only} and \textit{native-only}
shows whether one source changes the contribution of the other.

\paragraph{Clean-static sensitivity}

After the main $2\times2$ comparison, one additional sensitivity test examines
whether the static feature set contains too many overlapping descriptions of
workload. Its feature set was fixed before the test was run. The model keeps
the visit and location attributes together with demand and utilisation for the
RMG, VC, and MT areas. It excludes terminal-wide gate measures and variables
derived from the target area, including bins and ranks. ProSiT's native
workload features also remain disabled. The model is compared only with
\textit{visit-only} to determine whether this smaller static feature set changes
the earlier conclusion. It is not used as an additional candidate in the main
model-selection procedure, and no other feature combinations are tested.

\paragraph{Treatment of correlated attributes}

Correlation does not trigger automatic threshold-based feature deletion.
Decision-tree discovery does not require mutually independent predictors, and
several correlated CTB variables have distinct operational meanings. Their
presence does, however, make attribution to an individual split non-unique
because the tree can select one of several substitute predictors. The analysis
therefore proceeds at the level of semantically defined information sources.
The factorial design isolates static workload proxies from ProSiT's native
dynamic state, while the clean-static sensitivity removes alternative
aggregate, target-derived, binned and ranked representations within the static
source. Case attributes are sampled as observed joint tuples rather than as
independently fitted marginals, thereby preserving their empirical dependence
structure. Retained splits are reported as an inventory of rules used by a
particular fitted model, not as unique causal effects of individual
attributes. Exact minute-level joins additionally prevent future observations
from entering a case through interpolation or nearest-time matching. This is a little
temporal-integrity security rather than a decorrelation procedure.

\subsection{Pre-Specified Historical-Fidelity Selection}

The four configurations are discovered on the 64\,\% training partition and
compared on the subsequent 16\,\% validation partition. Selection uses four
primary errors that cover complementary perspectives, with turnaround EMD,
frequency-weighted yard-service EMD, yard-activity-rate L1 error, and
completion-order NGD ($N=3$). Paired differences use the common seeds 42--51.
An additional state source replaces the workload-blind \textit{visit-only}
candidate only if its 95\,\% paired interval shows an improvement in at least
one primary error and no paired interval shows a deterioration in another.
If several candidates satisfy this rule, the configuration with fewer added
state sources is preferred, followed by lower mean NGD. If none satisfies it,
\textit{visit-only} is selected. This conservative rule is fixed before the
validation results are inspected. It reflects the burden of justifying extra
state and prevents an unresolved improvement in one metric from overriding a
resolved loss in another. The untouched test partition has no role in this
decision. This rule selects the historical reference used to answer RQ1. It does not establish
that the same configuration is adequate for an intervention whose mechanism
requires endogenous system state.

\subsection{Intervention-Specific Mechanism Adequacy}
\label{sec:scenario_model_adequacy}

The pre-specified RQ3 rule selects a historical-fidelity benchmark. It assigns
no value to whether a configuration contains the mechanism required by a later
intervention and is therefore not, by itself, a complete selection rule for
simulation-based decision support. This limitation became visible when the
selected \textit{visit-only} configuration remained insensitive even under
extreme arrival compression.

An exploratory audit was consequently added. It evaluates eligibility from the
model specification rather than selecting a configuration because it produces
the expected scenario response. For the demand intervention, structural
eligibility requires simulated arrival changes to update an endogenous state
variable that is available to a fitted timing or resource-selection model.
\textit{Visit-only} has no such state. The demand and utilisation attributes in
\textit{static-only} are sampled historical case context and do not update when
simulated congestion changes. \textit{Native-only} and \textit{both} contain
ProSiT's endogenous workload and queue state. \textit{Native-only} is used as
the minimal eligible configuration because \textit{both} additionally contains
static proxies that are not changed by the intervention.

Once the adaptive audit was defined, this role assignment was based on semantic
eligibility rather than on the size or direction of the subsequent demand
response. Had \textit{native-only} remained invariant, that would have been
reported as a negative result rather than grounds for trying progressively
richer configurations. The candidate also satisfies the common Petri-net,
sequential-case, and RMG-cap requirements. Its validation differences from
\textit{visit-only} are small and not statistically resolved. This is only a
historical-fidelity screen. It is not evidence of equivalence or
non-inferiority because no margins were specified in advance.

The T22 intervention requires a different mechanism. Removing a resource label
is executable in every configuration, but none represents persistent container
location, physical relocation, or the resulting travel and contention. The T22
experiment is therefore a resource-configurability probe from the outset, not
an evaluation of a physically adequate block-closure model.

The audit remains adaptive because it was formulated after the workload-blind
stress diagnostic. It is not an independently confirmed selection procedure.
The demand ladder tests the narrower question of whether an eligible fitted
model propagates changed arrivals internally. Any observed pathway from
arrivals through queue state to a waiting distribution remains statistical
rather than a validated physical CTB queue mechanism.

The terminology used below reflects these separate roles. The
\emph{control-flow model} is the expert-repaired Petri net shared by every
configuration. The \emph{historical reference} is the selected
\textit{visit-only} parameter bundle for RQ1. The \emph{minimal endogenous-state
configuration} is the \textit{native-only} bundle used to test demand
propagation for RQ4. The T22 bundle is described as a resource-configurability
probe. None is treated as one universally best or final model for the study.

\subsection{Authoritative Parameter Bundle and Serialization Contract}
\label{sec:authoritative_parameter_bundle}

In this thesis, \emph{authoritative parameter bundle} is an operational
reproducibility term, which describes the exact executable
\texttt{SimulatorParameters} state loaded by the validation and scenario
scripts. If a derived table, JSON summary and executable state disagree,
the serialized object that generated the reported simulations is
the source of truth. Two provenance layers are distinguished. The four frozen
64\,\%-training bundles are authoritative for the RQ3 comparison on the
16\,\% validation period. The configurations required for the reported RQ1
and RQ4 roles are then rediscovered on the combined 80\,\% development
period. The
rediscovered \textit{visit-only} bundle is authoritative for the RQ1
historical test. The rediscovered \textit{native-only} bundle is authoritative
for the RQ4 demand-mechanism analysis. Neither role is assigned from performance on
the final test period.

Each freely discovered 80\,\% source bundle is retained unchanged. The
effective execution reference is a deep copy in which the RMG concurrency
values are capped at the domain maximum of three. It is stored as
\texttt{params\_baseline\_rmg\_max\_concurrency\_3.pkl} beside its two
scenario derivatives. A machine-readable model-role manifest records the
source and derived SHA-256 hashes, split roles, seeds and result directories.
The discovered overlap capacities remain
auditable without being mistaken for physically feasible capacities. All
executable bundles contain the Petri net and markings, routing and
resource-selection rules, resource mappings and capacities, calendars,
distribution objects, calibration metadata and the empirical sample arrays
used for stochastic draws.

The ProSiT JSON export is retained as the portable, human-inspectable
representation supported by the framework. For the final CTB bundles,
the round-trip audit in
\path{artifacts/json\_roundtrip\_audit\_final\_ctb\_20260831/roundtrip\_summary.csv}
confirmed that the fitted rule structures, resource capacities, calendars,
workload flags and empirical case-attribute distributions are reconstructed
consistently. It also showed a CTB-specific difference that matters for exact
numerical reproduction, where each frozen pickle contains 39 runtime rule nodes
with empirical \texttt{sampled} arrays, including 71,530 calibrated arrival
samples, whereas the corresponding object immediately after
\texttt{from\_json()} contains no sampled nodes. The serializer removes these
arrays and the runtime can regenerate them lazily from the stored fitted
distributions. Consequently, a JSON-reconstructed object is a valid portable
description of the discovered model, but it is not guaranteed to be
numerically identical to the post-calibration object that produced the CTB
results. The pickle is therefore the authoritative execution snapshot for
the reported experiments, while JSON remains the inspection and interchange
format. This is an observed property of the exact CTB bundles and installed
ProSiT version, not a claim that JSON is generally inferior to pickle.

The companion files \texttt{prosit\_run\_summary.json},
\texttt{control\_flow\_contract.json} and
\texttt{ctb\_calibration.json} document provenance and intended changes.
Validation and scenario scripts record SHA-256 hashes of their source
pickles, and scenario bundles are produced by deep copy rather than by
mutating the frozen baseline. The audit script and manifest are included
with the thesis artefacts so that the reported distinction can be checked
independently. Pickle is Python- and class-version-specific and must never
be loaded from an untrusted source. Reproducibility requires the recorded
software environment. These limitations explain why both formats are
retained, as JSON supports transparent inspection, while pickle preserves the
exact trusted runtime snapshot.

\section{Monte-Carlo Replication Protocol}
\label{sec:mc_protocol}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Every ProSiT simulation includes stochastic draws from the fitted
distributions. One Monte-Carlo draw is not enough to conclude that one configuration is more faithful than
another, when the observed difference may be within the sampling variance
of the simulator itself. This is the same many-possible-realisations
problem addressed by the multi-log validation design of
Chapela-Campa et al. and by classical independent-replication output
analysis \cite{ChapelaCampa2023Trust,Law2015Simulation}. This thesis
reports Monte-Carlo confidence intervals for the final fidelity estimates
and for the planned configuration and scenario contrasts.

\subsection{Replication Design}

The same replication design is used for all four ProSiT configurations:
\begin{equation}
\mathcal{C}=\{\textit{visit-only},\ \textit{static-only},\
\ \textit{native-only},\ \textit{both}\}.
\end{equation}
For each configuration $c\in\mathcal{C}$, the stored parameter bundle is
loaded and a fresh simulation engine is created. Ten runs are generated with
the seeds $s_i=42+i$ for $i=0,\ldots,9$. During configuration selection, each
run represents the 16\,\% validation window and contains 14,314 cases. After
selection, the rediscovered reference model is evaluated in ten runs over the
untouched 20\,\% test window, beginning at
$t_{\mathrm{start}}=\text{2026-04-20 18:17:00}$ and containing 17,892 cases.
The applicable start time and case count are read from the split manifest so
that each simulated log matches the real partition against which it is
evaluated.

ProSiT initializes each replication with the Petri-net initial marking, no
active cases and empty resource schedules. It does not reconstruct trucks that
entered before the temporal cutoff and were still inside the terminal at that
instant. The comparison therefore evaluates a terminating simulation started
at the observed boundary, not a fully observed steady-state snapshot. This
initial-condition limitation can affect the earliest generated cases and is
reported as such. It is shared by all configurations and all matched scenario
runs, so paired intervention effects are not created by different warm-up
states. A future operational deployment should initialize the engine from live
work in progress or use a documented warm-up period.

Let $m_{c,i}$ be one fidelity metric for configuration $c$ and seed $s_i$.
The reported value is the mean across the $N=10$ runs. Its 95\,\% Student-$t$
confidence interval is calculated as
\begin{equation}
    \bar{m}_c=\frac{1}{N}\sum_{i=0}^{N-1}m_{c,i},
    \qquad
    \mathrm{CI}_{95\%}=\bar{m}_c \;\pm\;
    t_{0.975,N-1}\frac{s_{m,c}}{\sqrt{N}},
\end{equation}
where $s_{m,c}$ is the sample standard deviation across the runs. This keeps
the comparison identical across configurations and separates the reported
mean from the simulator's run-to-run variation.

Because every configuration uses the same ten seeds, factor effects are
estimated as paired contrasts. For metric $m$, configurations $c_1$ and
$c_0$, and seed $s_i$, let
\begin{equation}
d_i=m_{c_1,i}-m_{c_0,i}.
\end{equation}
The mean and Student-$t$ interval are calculated over the ten $d_i$ values.
Pairing removes seed-to-seed variation shared by both configurations. Static
effects are estimated with native state off and on. Native effects are
estimated with static proxies off and on. Their interaction for outcome $Y$
is
\begin{equation}
 I=(Y_{\mathrm{both}}-Y_{\mathrm{static}})
   -(Y_{\mathrm{native}}-Y_{\mathrm{visit}}).
\end{equation}
The clean-static sensitivity uses the identical split, execution contract and
seeds.

\(N_{\text{seeds}}=10\) is used for every configuration. Independent
replications are the standard output-analysis unit for a terminating
stochastic simulation because each run provides one independent observation
of the statistic generated by the fixed input model \cite{Law2015Simulation}.
Ten replications also match the multi-log validation design used for business
process simulation while remaining computationally feasible for the
17,892-case CTB evaluation window \cite{ChapelaCampa2023Trust}. The
Student-$t$ interval is appropriate because the reported quantity is the mean
of replication-level metrics and the simulation variance is estimated from a
small sample. It is used as a transparent uncertainty summary, not as evidence
that ten runs identify input-model or discovery uncertainty. Those sources of
uncertainty remain outside the interval. All intervals are pointwise. They do
not provide simultaneous coverage across the complete set of metrics and
scenarios. The base seed is 42.

The choice to seed Python's \texttt{random} and \texttt{numpy.random}
before each \texttt{engine.apply()} rather than the ProSiT engine
itself is intentional, ProSiT 1.0.3 does not expose a per-call seed on
its simulation engine. Seeding both random-number generators before the
call yields reproducible replications and captures the same stochastic
variability that a user would observe in production.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Evaluation Metrics}
\label{sec:evaluation_metrics}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The comparison of a simulated event log against the real held-out log uses complementary distributional and point-statistic measures.
Each metric is computed once per Monte-Carlo replication so that a confidence interval can be attached to the point estimate.

The metric set follows the intended use of the model rather than collapsing
validity into one score \cite{Sargent2013Validation,Chapela2025SimQuality}.
Conformance and the case contract assess whether the control-flow language can
represent the terminal process. Activity-rate L1 and NGD assess what the
simulator actually generates within that language. Wasserstein distances
assess the complete timing distributions in their natural unit of minutes,
while mean, median and P90 errors remain directly interpretable for terminal
management. Bottleneck decomposition then locates accumulated time without
claiming that an observational gap is a causal queue. Reporting these views
separately avoids an arbitrary weighted validity index and makes trade-offs
between structural, temporal and operational fidelity visible.

\paragraph{Wasserstein Distance (EMD)}

For each yard activity $a$ the service-time EMD is
\begin{equation}
    \text{EMD}_a^{\text{svc}} = W_1
    \bigl(F_{a}^{\text{sim,svc}}, F_{a}^{\text{real,svc}}\bigr),
\end{equation}
where $F_{a}^{\text{sim,svc}}$ and $F_{a}^{\text{real,svc}}$ are the
empirical CDFs of $\text{time}-\text{start}$ for activity $a$ in the
simulated and real log, respectively. Gate In and Gate Out are excluded
from the service-fidelity aggregation because both have zero-duration
timestamp constructions and would mechanically improve the score without
representing terminal handling. Let $\mathcal A_Y$ be the set of yard
activities and $n_a^{\mathrm{real}}$ the number of valid held-out
observations. This thesis reports all per-activity values and two yard-level
aggregates:
\begin{align}
 \overline{\mathrm{EMD}}_{Y}
   &= \frac{1}{|\mathcal A_Y|}\sum_{a\in\mathcal A_Y}
      \mathrm{EMD}^{\mathrm{svc}}_a,\\
 \overline{\mathrm{EMD}}_{Y,w}
   &= \frac{\sum_{a\in\mathcal A_Y} n_a^{\mathrm{real}}
      \mathrm{EMD}^{\mathrm{svc}}_a}
      {\sum_{a\in\mathcal A_Y} n_a^{\mathrm{real}}}.
\end{align}
The first gives every yard-activity class equal influence. The second
describes the error experienced by the empirical mix of yard events. The
case-level turnaround EMD
is $W_1(F^{\text{sim,ttot}}, F^{\text{real,ttot}})$ where
$\text{ttot}$ is the total elapsed time per case (first start to last
complete). The inter-arrival EMD is
$W_1(F^{\text{sim,iat}}, F^{\text{real,iat}})$ where
$\text{iat}$ is the time between consecutive case-arrival timestamps.
All EMDs are reported in minutes. The main view retains durations up to
24 hours and is accompanied by an uncapped raw view so that an artificial
simulation tail cannot be hidden.

\paragraph{Kolmogorov--Smirnov Statistic}

For each distribution pair the two-sample KS statistic is computed by
\texttt{scipy.stats.ks\_2samp}. Because the CTB test log contains 55,360
events, sub-sampling is applied so that each side contributes at most
$10{,}000$ observations to the test. This limits computational cost and
the extreme sample-size sensitivity of the associated significance test.
It does not turn the $p$-value into a fidelity effect size. The KS
statistic (magnitude of the maximum vertical CDF gap) is reported
alongside the EMD as the main measure. The $p$-value is retained
only as a secondary diagnostic.

\paragraph{Point-Statistic Errors}

For each activity and each case-level KPI the mean, median and 90th
percentile of the simulated and real distributions are compared as
absolute and relative errors. This complements the distributional
metrics with operationally interpretable point statistics
(e.g.\ ``the simulator under-predicts mean turnaround by $X$ minutes'').

\paragraph{Yard-Activity-Rate L1 Error}

Control-flow fitness shows whether a real trace is permitted by the Petri net,
but it does not show whether the simulator generates the yard activities with
the observed frequencies. Let $\mathcal A_Y$ be the union of non-gate activity
classes in the two logs. For log $L$, activity $a\in\mathcal A_Y$, event
count $N_a(L)$ and case count $N_C(L)$, define the activity rate
\begin{equation}
    r_a(L)=\frac{N_a(L)}{N_C(L)}.
\end{equation}
The reported yard-activity-rate error is
\begin{equation}
    E_{\mathrm{rate},1}
    =\sum_{a\in\mathcal A_Y}
      \left|r_a(L_{\mathrm{sim}})-r_a(L_{\mathrm{real}})\right|.
\end{equation}
Because repeated activities are allowed, these are events per case rather than
probabilities and the sum is not constrained to equal one. Lower error means
that the simulator reproduces the empirical activity mixture and repetition
rates more closely. Gate In and Gate Out are excluded because the case contract
requires exactly one of each and would otherwise add no discriminatory value.

\paragraph{N-Gram Distance (NGD), with $N=3$}

NGD compares local activity-order frequencies in the generated and held-out
logs \cite{ChapelaCampa2023Trust,Chapela2025SimQuality}. Each case sequence is
padded at both boundaries with $N-1$ dummy activities. Let $C_L(g)$ be the
count of $N$-gram $g$ in the resulting profile of log $L$. The distance is
\begin{equation}
    \operatorname{NGD}_N(L_1,L_2)
    =
    \frac{\sum_g\left|C_{L_1}(g)-C_{L_2}(g)\right|}
         {\sum_g C_{L_1}(g)+\sum_g C_{L_2}(g)}.
\end{equation}
It lies in $[0,1]$, with zero indicating identical $N$-gram count profiles. The
primary analysis uses $N=3$. Unlike directly-follows pairs, triples retain the
local predecessor--activity--successor context, while remaining substantially
less sparse than longer subsequences for the CTB activity set. The primary
profile orders events by completion timestamp with stable explicit/input-order
tie breaking, matching the published metric convention. The ITS
schedule-derived case order stored in XES is retained as a sensitivity because
three held-out cases contain small
timestamp inversions. NGD complements, rather than replaces, complete-trace
conformance and the case-language contract.

\paragraph{Frequency-Weighted Bottleneck Decomposition}

The held-out log is additionally decomposed to locate where elapsed truck time
accumulates. For each event, recorded service is completion minus start. The
non-negative gap between the previous event's completion and the current
event's start is defined as composite pre-service delay. Under the sequential
case contract, the sums of service and composite pre-service delay reconstruct
case turnaround exactly. Activities are ranked by accumulated minutes, equal
to event frequency multiplied by their mean contribution, and are accompanied
by median and p90 values. This prevents a rare but long event from being called
the dominant bottleneck solely because of its mean.

The gap is not interpreted as pure queueing. It may combine movement,
traffic or transfer, dispatching, and resource waiting. Resource-level overlap
at event start is reported as a separate diagnostic against the cap of three,
but overlap in a pooled block label is not treated as a physical crane count.
Its causal scope is limited to identifying accumulation points that require
further physical modelling. For the sequential CTB net, this observed gap is
also the direct structural counterpart of the simulated interval from
\texttt{enabled:timestamp} to \texttt{start:timestamp}. Their activity-specific
means are compared for the principal RMG handling patterns using the existing
ten baseline replications. The real mean is treated as fixed and the
Monte-Carlo interval covers seed-wise variation of the simulated mean. This is
an endpoint-fidelity diagnostic, not validation of a physically observed
enablement timestamp.

A targeted \texttt{LL\_mixed} audit complements the aggregate ranking. It
counts its position and direct successors in both temporal partitions and
compares a successor's composite pre-service gap after \texttt{LL\_mixed} with
the same activity after other predecessors. This describes whether the rare
branch is associated with a distinct downstream time burden. It does not turn
seven multi-yard observations into a mandatory routing rule. The same metric
definitions are reused for single-run diagnostics and multi-seed evaluation so
that their values remain directly comparable.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{What-If Scenario Design}
\label{sec:what_if_design}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The operational value of a logistics simulation lies in comparing future
decisions under conditions that cannot safely be tested in the live terminal.
The intended workflow begins with a forecast operating condition, compares
candidate policies through simulated process executions, and evaluates their
activity- and system-level consequences. A forecast of high yard utilisation could, for
example, motivate a reduction in truck slots released per hour or a temporary
policy that favours retrieval-related handling. A useful model must then show
not only total turnaround but also whether receive and delivery service or
pre-service delay change differently. These disaggregated effects are essential:
an acceptable terminal-wide average can conceal a harmful shift for one
handling pattern.

Two independent interventions are evaluated to address RQ4. Both are derived
by deep copy from the calibrated \textit{native-only} bundle rediscovered on
the complete 80\,\% development period. Section~\ref{sec:scenario_model_adequacy}
explains why this bundle is used as a minimal endogenous-state configuration
for the demand mechanism test rather than as a validated counterfactual model.
The cap-three \textit{visit-only} bundle is retained as the workload-blind
negative control.
The RMG ceiling is applied to a deep copy before either intervention is
derived. Neither the observed test outcomes nor the scenario outcomes are used
to fit a scenario parameter. The experiments are deliberately simple tests of
internal parameter propagation rather than proposed operating policies or
validated forecasts.

Both interventions use inspectable ProSiT parameters, but they do not exercise
the complete white-box intervention space. Scenario~A changes a resource
mapping and availability calendar. Scenario~B changes the empirical samples in
the arrival model's single leaf. Neither scenario edits a learned condition,
changes a split threshold or replaces a subtree. The experiments therefore
test transparent parameter configuration and response tracing. They do not
claim to demonstrate every form of white-box rule interaction proposed for
ProSiT.

\subsection{Scenario A: T22 Resource-Pool Reallocation}

Scenario A represents a temporary loss of T22 availability, as may occur during
construction work or following a system, infrastructure or mechanical failure.
T22 is removed from every \texttt{params.act\_to\_resources} entry that
references it. The implementation first verifies that each affected activity
retains at least one eligible resource. All 168 weekly calendar slots of T22
are then set to unavailable. All other parameters are unchanged.

This is a resource-pool reallocation experiment, not a complete
spatial yard-closure model.
The discovered selector may use target-area attributes as statistical
predictors, but ProSiT does not impose a hard constraint that binds a
container to its historical storage block. A truck whose
historical target was T22 can be assigned to another eligible
block without an explicit container-relocation operation or a
location-dependent travel-time adjustment. This boundary is discussed in
Section~\ref{sec:limitations}.

\subsection{Scenario B: 20\,\% Higher Truck Demand}

Scenario B changes only the empirical working-time inter-arrival
distribution. For demand multiplier $m=1.20$, every empirical
inter-arrival sample $x_i$ is replaced by $x_i/m$. This preserves the
zero mass and the empirical distribution shape while increasing the
modelled arrival intensity by exactly 20\,\%. The gate-admission
calendar, process model, duration models, routing, resource mappings,
resource calendars and case-attribute schema remain unchanged. The
scenario is independent of the T22 resource-pool reallocation. Operationally,
the admitted truck rate is a quantity a terminal can influence in advance
through the number and timing of appointment slots and the gate lanes made
available for admission. The management question is how many trucks per hour
can be admitted before delay becomes operationally unacceptable under the
forecast terminal state. Because the available log does not contain individual
slot bookings, rejection decisions or gate-lane service, this scenario
represents a change in effective admitted arrival intensity. It is not a
detailed model of a particular appointment or lane-opening policy.

\paragraph{Domain-Constrained RMG Capacity}

The freely discovered serialized source assigns maximum concurrency four
to ten RMG block identifiers and five to twelve, for an aggregate effective
upper bound of 100. ProSiT obtains these numbers from overlapping timestamps.
They are empirical concurrency proxies rather than equipment counts. They
exceed the hard physical upper bound of three RMGs per block, which was
confirmed by operational experts from the terminal. For both reported model
roles, the effective execution bundle replaces every RMG value $c_r$
with $\min(c_r,3)$. The aggregate upper bound becomes $22\times3=66$. This
does not assert that three cranes normally serve landside trucks: in regular
operation two cranes may serve the waterside and at most one may serve the
landside, but that allocation depends on ship operations and is not observed
in this event log. Three is a reasonable physical ceiling, not an
estimated landside staffing level. No resource
mapping, calendar, selection rule, timing model, arrival model or
control-flow parameter is changed. The T22 and demand interventions are then
independently derived from the capped \textit{native-only} baseline.

The expert confirmation applies to the ceiling, not to the learned HO2 and LL
concurrency values, the post-discovery choice to keep all 168 weekly
resource-calendar slots open, or the simulator's assignment and queue
semantics. Those quantities remain empirical or technical abstractions and are
evaluated as such.

This is a transparent domain constraint rather than a data-driven
recalibration. The freely discovered source remains frozen as discovery
evidence, whereas the cap-three copies are the effective execution bundles. A
matching uncapped copy of the historical \textit{visit-only} model is
evaluated on the same test period with identical seeds, trace counts and start
time. This paired sensitivity determines whether the physical cap materially
changes the reported historical fidelity. It does not use the test result to
choose or fit the cap. The ceiling is retained because it is a validated
domain constraint.

\paragraph{Capacity-Pressure Diagnostic}

The demand intervention is additionally checked against block-level offered
load in the held-out log. For each observed RMG block $b$, event rate
$\lambda_b$, mean recorded service time $E[S_b]$, and the physical ceiling
$c_b=3$ define the nominal utilisation diagnostic
\begin{equation}
    \rho_b=\frac{\lambda_b E[S_b]}{c_b}.
\end{equation}
If routing and service remain fixed, the 20\,\% intervention implies
$\rho_b'=1.2\rho_b$. This calculation does not estimate queueing time and is
not used to calibrate the scenario. It tests whether the intervention even
approaches mean saturation under the capacity assumption. A separate
minute-grid overlap check reports the observed share of time at or above
capacity. It is interpreted cautiously because minute-resolved timestamps
can create or hide short overlaps and because block identifiers are not crane
trajectories.

\paragraph{Demand-Saturation Ladder}

Because the offered-load diagnostic places nominal mean saturation near a
realised elapsed arrival-rate ratio of 2.37, a separate stress test evaluates
$m\in\{1.0,1.2,1.5,2.0,2.4,3.0\}$. Every level is derived independently from
the cap-three \textit{visit-only} and \textit{native-only} bundles by replacing
each empirical working-time inter-arrival sample $x_i$ with $x_i/m$. The
process net, case volume, seed, resource mappings, capacities, calendars,
duration models, and case-attribute generation remain fixed. Ten matched seeds
produce 60 runs per configuration and 120 runs in total. Structural case
contracts are enforced at every level. Duration tails above 24 hours are
reported rather than rejected because they may be a substantive outcome under
deliberate overload.

The configured value $m$ scales working-time inter-arrivals. It is not assumed
to equal the arrival-rate multiplier measured over elapsed calendar time,
because gate closures remain fixed and the simulated horizon shortens as
demand rises. Both quantities are therefore reported. The capacity comparison
and response-curve x-axis use the realised elapsed-rate ratio relative to the
matched baseline. This places the response on the same scale as the independent
2.37 offered-load estimate.

This ladder is a diagnostic response-surface experiment, not a forecast that
CTB would admit two or three times its observed truck volume. It distinguishes
an intervention that is simply too modest to reach the model's capacity region
from a simulator that fails to propagate demand pressure even when the
nominal offered-load threshold is crossed. The intervention also has a direct
operational interpretation. Terminal management cannot choose the realised
arrival process exactly, but it can influence the admitted truck rate through
slot availability and the number of staffed gate lanes. The response curve
therefore asks at which offered arrival rate the simulated terminal moves from
absorbing additional demand to accumulating material congestion. Its higher
levels are stress-test points used to identify that transition, not proposed
operating plans.

\paragraph{Design Limitations of the Fixed-Case-Count Ladder}

The design keeps the number of generated cases fixed at 17,892 while
compressing working-time inter-arrivals.  This is a compressed-arrival-horizon
experiment, not a pure steady-state capacity test.  In addition to raising
arrival intensity, it changes where arrivals fall relative to operating hours,
the exposure to gate-closure periods, end-of-horizon effects, and the
composition of cases completing within the observation window.  The reported
transition region consequently reflects the combined effect of these factors,
not resource capacity alone.  A cleaner alternative would use a fixed
observation horizon and vary the arrival rate with sufficient warm-up and
run-out periods.  ProSiT's current engine initialises from an empty state
(Section~\ref{sec:mc_protocol}) and does not support a documented
warm-up discard, so that alternative is not available without framework
modification.  The compressed-horizon design is therefore retained as the
feasible diagnostic, and its confounds are noted when the transition region is
interpreted in Section~\ref{sec:results_saturation}.

\paragraph{Reporting}

All central simulation tables use the same deterministic execution path. In
addition to setting NumPy and Python seeds, the execution adapter orders
equally weighted enabled transitions before drawing
from ProSiT's routing probabilities. This removes dependence on Python set
iteration without changing the Petri net, learned probabilities or random
draw. Historical fidelity, the four-cell feature-source experiment, cap sensitivity,
both policy scenarios and the demand ladder are therefore
derived from one runner contract. A machine-readable provenance manifest in
the research project records the source-bundle and result-file hashes, seeds,
trace count and authoritative result directories.

Baseline and both interventions are executed with ten matched seeds
(42--51), $n_{\text{traces}}=17{,}892$ and
$t_{\text{start}}=\text{2026-04-20 18:17}$. All paired deltas use
common random numbers. Mean, median and 90th percentile of turnaround,
RMG service and RMG pre-service delay are reported together with the
observed arrival KPIs. For the T22 experiment, service and pre-service
effects are reported separately for
\texttt{RMG\_receive} and \texttt{RMG\_delivery}. Every generated log in
either model role is subjected
to the sequential case contract of
Section~\ref{sec:process_discovery_methodology}. Any violation aborts
the run. The 24-hour threshold used for robust historical distance metrics is
not a physical case contract. Simulated service events or visits above it are
retained in raw scenario KPIs and reported by seed and scenario instead of
being silently removed or replaced. A separate diagnostic invocation with
\texttt{--no-rmg-cap} reproduces the uncapped \textit{visit-only}
historical-reference baseline from the same
80\,\%-development source bundle. The capacity comparison verifies identical
source hashes, seeds and settings before computing the paired
cap-three-minus-uncapped effects. These uncapped results are diagnostic only
and are excluded from configuration selection. The 30 \textit{native-only}
cap-three scenario logs form the primary RQ4 scenario evidence. The matching
30 \textit{visit-only} logs are the workload-blind negative control. The 120
demand-saturation replications are stored separately and interpreted as a
diagnostic stress test rather than a third operational policy scenario.

To isolate the contribution of native dynamic state, the cap-three
\textit{visit-only} and \textit{native-only} models use identical seeds. For
configuration $c$, demand level $q$, and seed $i$, the paired response is
$d_{c,q,i}=Y_{c,q,i}-Y_{c,0,i}$. The configuration sensitivity is then the
difference-in-differences
\begin{equation}
    D_{q,i}=d_{\textit{native-only},q,i}
             -d_{\textit{visit-only},q,i}.
\end{equation}
Student-$t$ intervals over the ten $D_{q,i}$ values distinguish a response
attributable to access to native dynamic state from ordinary Monte-Carlo
variation in either bundle.

\section{ProSiT Implementation Notes and Workarounds}
\label{sec:prosit_workarounds}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Applying ProSiT 1.0.3 \cite{Vinci2026prosit} to the CTB event log
uncovered several implementation issues that would have propagated as
silent misbehaviour if not addressed. This section documents them so
that the experiments can be reproduced deterministically and so that the
downstream fidelity numbers can be interpreted correctly.

\paragraph{Data-Attribute Discovery on NaN Columns}

The default \texttt{attribute\_mode='distribution'} passes each case
attribute through a per-attribute distribution fitter. In the CTB log,
\texttt{full\_ratio} and \texttt{is\_full} contain \texttt{NaN} for
cases that involve empty-container-only visits. The distribution fitter
in ProSiT 1.0.3 forwards the raw values to
\texttt{scipy.stats}, which raises
\texttt{TypeError: ufunc 'isfinite' not supported} on the mixed
dtype. Switching to \texttt{attribute\_mode='empirical'} bypasses the
per-attribute fitter and samples full attribute tuples from the
observed joint distribution instead. This is not a fidelity compromise:
the discovered simulator still preserves case-level attribute
correlations, and empirical sampling from the training distribution is
the appropriate choice given the number of categorical attributes
present in the CTB log.

\paragraph{Temporal Features Outside the ProSiT Input}

The final discovery contract does not pass hour-of-day or day-of-week
attributes to ProSiT. It keeps the five standard event-log columns and the
approved visit-related, demand, utilisation and target attributes from
Table~\ref{tab:eventlog_attributes}. Other columns are removed before
simulation-parameter discovery. Hour and weekday are derived from timestamps
only in the separate arrival and explanatory analyses. The retained ProSiT
configurations therefore do not condition their timing rules directly on
calendar features. This is an input-model boundary when interpreting the
day/night differences reported in Section~\ref{sec:results_arrival_process}.

\paragraph{Non-Deterministic Simulation Engine}

\texttt{SimulatorEngine.apply()} does not accept a seed argument. The
Monte-Carlo protocol of Section~\ref{sec:mc_protocol} seeds
Python's \texttt{random} and \texttt{numpy.random} before every call to
\texttt{apply()}. Seeding alone is insufficient across Python processes,
however. ProSiT obtains enabled transitions from a set, while PM4Py hashes
transition objects by in-memory identity. After a model is reloaded, the same
enabled transitions can therefore be presented to the weighted sampler in a
different order and consume the same random draw differently. The deterministic
execution adapter canonicalises this list by the stable Petri-net transition name
immediately before the existing weighted draw. It changes neither the net nor
the learned transition weights. Independent fresh-process runs with the same
seed then produce identical result tables. This stable ordering, together with
the two random seeds, is the reproducibility guarantee used for the scenario
results in Chapter~\ref{chap:results}.

\paragraph{Contribution Boundary}

The ProSiT engine itself was not modified for these workarounds. The
CTB pipeline patches its own callers so that ProSiT can be invoked
without source-code changes. The workarounds and the documented input boundary
constitute the technical adaptation of ProSiT to the CTB case study. They are
listed here so that a reader can distinguish the contribution of this
thesis (case-study specific data engineering, held-out validation
methodology, multi-seed replication, sensitivity analysis, what-if
scenario protocol) from the contribution of ProSiT itself (automatic simulation-parameter discovery from event logs \cite{Vinci2026prosit}).
