This appendix separates visual process inspection from executable model state.
The complete directly-follows graph exposes every observed training-log
relation. The graph is descriptive; the discovered Petri net and fitted ProSiT
parameters define the executable simulation model.

\section{Unfiltered Training-Log Control Flow}

Figure~\ref{fig:appendix_full_dfg} shows the unfiltered 59-arc directly-follows
graph of the order-preserving training log. It is included for audit because
the dominant-frequency view in Chapter~\ref{chp:experiments_and_framework}
deliberately suppresses rare relations. The complete view confirms the fixed
gate boundary and makes low-frequency repetitions and cross-activity relations
inspectable. Its density also demonstrates why it is unsuitable as the primary
explanatory figure. It is a descriptive view and should not be interpreted as a Petri net. In particular,
a directly-follows arc records observed succession but does not encode choice,
concurrency, markings, or firing rules.

\section{Executable Model State}

The baseline, T22-closure and increased-demand models are retained as separate
serialized ProSiT parameter objects. The baseline contains the common Petri
net, markings, fitted distributions, resources, capacities and calendars.
The T22 scenario removes the block from the eligible RMG resource mappings and
its availability calendar. The demand scenario changes only the empirical
working-time inter-arrival sample. These state differences are described in
Section~\ref{sec:what_if_design}; no source-code listing is required to
interpret the interventions.

The public ProSiT save-and-load workflow serializes discovered parameters so
that simulation can be repeated without rerunning discovery
\cite{ProSiTRepository}. The project follows that workflow and additionally
retains the exact Python objects used for the CTB experiments. A round-trip
audit of all three final bundles is stored in
\path{artifacts/json\_roundtrip\_audit\_final\_ctb\_20260831/}. It found that fitted
rules, capacities, calendars, workload flags and empirical case-attribute
distributions survive reconstruction, but the 39 runtime rule nodes and their
71,530 calibrated arrival samples present in each pickle are absent
immediately after \texttt{from\_json()}. ProSiT can regenerate such samples
lazily from the fitted distributions, so the JSON remains a valid portable
model description. It is not, however, guaranteed to be numerically identical
to the post-calibration object used for the reported CTB runs. The pickles are
therefore the authoritative execution snapshots, while JSON is retained for
inspection and interchange. Pickles must only be loaded from this trusted
project state and with the recorded environment.

The serialized objects and provenance records are retained in the research
project and can be supplied separately if executable reproduction is requested.
They are not required to follow the methodological argument or the result
tables in the thesis.
